== 4. 設計方針

=== 4.1 プロバイダ抽象と OpenAI 互換クライアント

`OpenaiChatCompletion` を汎用化し、`base_url` を注入可能にする（llama-server は OpenAI 互換 API を話す）。

* `LlmClient`（仮）: `provider`（`:llama_cpp` / `:openai` / `:sd_cpp`）、`base_url`、`model`、`api_key`（任意）、`temperature` を受け取り、`/v1/chat/completions` を叩く薄いクライアント。
* 既存 `OpenaiChatCompletion` はこの上の薄いラッパ（後方互換）か、`LlmClient` へ寄せて段階的に置換。
* JSON 強制タスク（intent / query 生成 / sd プロンプト）向けに、`response_format`（対応時）または後段パースを備える。

=== 4.2 モデルレジストリ（設定）

dev note §7 の YAML を Rails 設定へ移す。**接続先・シークレットは Rails credentials、非機密の役割マッピングは `config/`** に置く方針（`AGENTS.md` の credentials 方針に整合）。

* 役割キー: `intent` / `fast_chat` / `main` / `vision` / `embedding`（Phase 5b）/ `image_generation`。
* 各役割: `provider` / `base_url` / `model` / `temperature`。
* development 既定は `http://localhost:100xx`（Tsuzura と同様に development では本番 URL を使わない）。
* アクセサ（例 `ChatModels.for(:intent)`）に集約し、`base_url` 等を散在させない。

=== 4.3 intent 分類とルーター

* `IntentClassifier`: LFM2.5 に dev note §3.1 の system prompt で JSON（`intent` / `confidence` / `needs_tool` / `reason`）を返させる。低温度。
* `ChatRouter`: intent → (モデル役割, ツール) のマッピング（dev note §2）。
* エスカレーション（dev note §5）: `confidence < 0.7` / 「不明」多発 / コード修正 / 複数資料比較 / 長文 / ユーザーが「詳しく・設計・仕様・実装」を要求 → **`main`(12B) へ昇格**。

=== 4.4 ツール層

intent とルーターから呼ぶツールを疎結合に定義（`Chat::Tools::*`）:

* `fetch_url`: `Net::HTTP` 取得 → 本文抽出（readability 相当）→ チャンク分割 → LFM2.5 一次要約 → E4B/12B 統合。
* `web_search`: SearXNG（`base_url` は credentials）。
* `rag_search`: **Phase 5a** — 既存 **pgroonga**（`Memo.search_text`）を lexical retriever に。LFM2.5 で query 生成（§3.3）→ 12B で最終回答（§3.6）。**Phase 5b** — **LFM2.5-Embedding-350M**（Liquid AI、1024 次元 dense bi-encoder、GGUF + llama-server `--embeddings`）でメモ本文チャンクをベクトル化し **pgvector** に格納。pgroonga 結果と dense 近傍をマージ（RRF 等）してセマンティック recall を上乗せ。ColBERT（LFM2.5-ColBERT-350M）はリランク用途で後追い検討。
* `image_analysis`: Qwen2.5-VL（§3.8）。
* `image_generation`: LFM/12B で sd プロンプト生成（§3.9）→ sd.cpp 実行。
* `memo_search` / `memo_add`: 既存メモ機能へのブリッジ。

=== 4.6 RAG 検索基盤（pgroonga 先行 → Embedding + pgvector）

dev note の「pgvector / Groonga」を、kbmemo の既存資産と Liquid AI の埋め込みモデルに合わせて具体化する。

==== Phase 5a: pgroonga（lexical、先行）

* 既存 `Memo.search_text`（`&@~` + `pgroonga_score`）をそのまま retriever に使う。マイグレーション・インデックスは `db/migrate/20260703101000_enable_pgroonga_on_memos.rb` が一次情報。
* 実装コストが低く、固有名詞・型番・エラー文・関数名など**キーワード一致**に強い。
* LFM2.5（`ModelRegistry.for(:intent)`）で検索クエリ生成（§3.3）→ ヒットしたメモ抜粋をコンテキストに → Gemma 4 12B（§3.6 `RAG_ANSWER`）で回答。

==== Phase 5b: LFM2.5-Embedding-350M + pgvector（semantic 上乗せ）

Liquid AI が 2026-06 に公開した retrieval 向けモデル（link:https://www.liquid.ai/blog/lfm2-5-retrievers[LFM2.5 Retrievers ブログ]、link:https://huggingface.co/LiquidAI/LFM2.5-Embedding-350M[Hugging Face]）。

[cols="1,2"]
|===
|項目 |内容

|モデル
|`LiquidAI/LFM2.5-Embedding-350M`（dense bi-encoder、~354M、1024 次元 CLS ベクトル、cosine）

|想定用途
|短コンテキスト検索（doc ~512 tokens）。メモ本文のチャンク単位インデックス向き

|実行
|GGUF + `llama-server --embeddings`（別ポート。例 `10034`）。`Chat::ModelRegistry` に `embedding` 役割を追加

|DB
|PostgreSQL **pgvector** 拡張。メモチャンクごとに `vector(1024)` を保持（`memo_id` / `chunk_index` / `content` / `embedding`）

|検索
|クエリを同モデルで embed → pgvector 近傍検索。pgroonga 結果と **RRF（Reciprocal Rank Fusion）** 等でマージし、lexical の弱点（言い換え・意味類似）を補う

|採用しない（当面）
|`LFM2.5-ColBERT-350M` — 精度は高いがトークン単位ベクトル + MaxSim で pgvector に素直に載らない。リランクが必要になった段階で検討
|===

* 埋め込みは **chat completions とは別プロセス**（`llama-server -hf LiquidAI/LFM2.5-Embedding-350M-GGUF --embeddings`）。`Chat::LlmClient` とは別アクセサ（例 `Chat::EmbeddingClient`）を検討。
* インデックス更新: メモ保存時に非同期ジョブでチャンク分割 + embed + upsert（初回はバックフィル rake タスク）。
* Phase 5b 完了後、`Chat::Prompts::RAG_ANSWER` の自動注入を有効化（検索結果がコンテキストに付与される前提が満たされる）。

=== 4.7 会話永続化（Phase 8）

現状のクライアントメモリを DB へ。最小テーブル案:

* `chat_conversations`（`account_id`、任意の `memo_id`、`title`、タイムスタンプ）。
* `chat_messages`（`conversation_id`、`role`、`content`、`intent`、`model_role`、`tool_calls`(JSON)、`created_at`）。

== 5. パイプライン（処理フロー）

dev note §4 を実装単位に落とす。

[source,text]
----
User 入力
  -> IntentClassifier (LFM2.5, 低温度, JSON)
  -> ChatRouter: intent -> {model_role, tools}
  -> [tool があれば] Chat::Tools::* を実行しコンテキスト付与
  -> 一次応答モデル (E4B or 役割別)
  -> エスカレーション条件を満たせば main(12B) で再生成
  -> 応答（+ 会話永続化）
----

=== Phase 0 実装メモ（完了）

* `Chat::LlmClient`（`app/services/chat/llm_client.rb`）— OpenAI 互換クライアント。`base_url` 注入可・`temperature`・`response_format`（JSON 強制）対応。ローカル llama-server は `api_key` 不要。
* `Chat::ModelRegistry`（`app/services/chat/model_registry.rb`）— 役割→接続情報。`ModelRegistry.for(:main).build_client` でクライアント生成。development/test は `base_url` 未設定時に localhost 既定ポート（§6）へフォールバック、production は credentials 必須。
* 役割マッピング `config/chat_models.yml`（非機密）、接続先/機密 `config/credentials/chat_models.example.yml`。
* 既存 `OpenaiChatCompletion`（BYOK）は Phase 0 時点では温存。UI 統合で `Chat::LlmClient` へ統合し撤去済み（<<ui,UI 統合>>）。

=== Phase 1 実装メモ（完了）

* `Chat::IntentClassifier`（`app/services/chat/intent_classifier.rb`）— LFM2.5（`ModelRegistry.for(:intent)`）に §3.1 の system prompt で JSON 分類させる。`response_format: json_object` を指定。コードフェンス混入や JSON 崩れ・LLM エラー時は `unknown` / `confidence 0.0` にフォールバックし、intent は許可リスト（`INTENTS`）で検証。
* `Chat::Router`（`app/services/chat/router.rb`）— §2 に基づき intent→`{model_role, tools}`。ツール名は Phase 3 以降の実装待ちで、ここでは返すのみ。
* `Chat::Escalation`（`app/services/chat/escalation.rb`）— §5 の昇格判定。`confidence < 0.7` / `code` intent / ユーザーが「詳しく・設計・仕様・実装」等を要求 / 一次応答に「不明」系が多い → `main`(12B) へ。既に `main` の場合は昇格しない。
* `Chat::Agent`（`app/services/chat/agent.rb`）— パイプライン本体。classify→route→一次応答→（条件を満たせば）main へ再生成。chat 応答不能な役割（vision / image_generation / nil）は当面 `main` にフォールバックしつつ `tools` / `pending_tools` を返し、ツール実装待ちを呼び出し側へ伝える。
* いずれも LLM クライアントを DI 可能にし、テストは HTTP を叩かずスタブで検証（ローカルサーバ不要）。
* **UI 未接続**: 本フェーズはコア services のみ。メモ編集パネル / 独立チャット画面への組み込みは別途 UI 統合フェーズで行う（ローカルサーバ稼働が前提のため）。

=== Phase 2 実装メモ（完了）

* `Chat::Prompts`（`app/services/chat/prompts.rb`）— dev note §3.1–§3.9 の全 system prompt を集約する唯一の定義元。`INTENT_CLASSIFIER` / `URL_PRIMARY_SUMMARY` / `RAG_QUERY` / `FAST_CHAT` / `MAIN` / `RAG_ANSWER` / `CODING` / `VISION` / `SD_PROMPT`。
* `Chat::Prompts.system_for(role:, intent:)` — 本応答の system prompt を決定。優先順位は **intent 固有 > 役割別（fast_chat/main/vision）**。intent 固有はツール不要で安全な `code`→CODING のみ自動注入し、外部コンテキスト前提の RAG_ANSWER / VISION は該当ツール実装（Phase 5a/5b / 6）まで注入しない。
* `Chat::IntentClassifier::SYSTEM_PROMPT` は `Chat::Prompts::INTENT_CLASSIFIER` を参照（定義の一本化）。
* `Chat::Agent` は明示 `system_prompt` が無ければ役割/intent に応じた既定を自動注入。エスカレーション時は `main` の prompt（code は CODING）を使う。
* temperature は Phase 0 の `ModelRegistry`（`config/chat_models.yml`）が役割ごとに保持し、`LlmClient` が送信（§8）。

== 6.5. UI 統合（メモ編集パネル）— 2026-07 完了

決定（§10.2）どおり、まずメモ編集サイドパネルをローカルモデル対応へ拡張した（汎用エージェント画面は後続）。

* **バックエンド選択**: `MemoAiChat` は既定でローカル `main` モデル（`ModelRegistry.for(:main)`）を使い、`Chat::LlmClient::ConnectionError`（サーバ未起動・タイムアウト）時のみ登録済み OpenAI キー（BYOK）へフォールバック。BYOK も同じ `Chat::LlmClient` 経由に統一し、`OpenaiChatCompletion` は撤去。
* **接続エラーの識別**: `Chat::LlmClient::ConnectionError < Error` を追加。API エラー（4xx/5xx）とネットワーク障害を区別し、フォールバック判定に使う。
* **コントローラ**: `MemoAiChatsController` は OpenAI キー必須の事前チェックを廃止（ローカルはキー不要）。`Chat::LlmClient::Error` を 422＋`settings_url` で返す。
* **UI**: `_ai_panel` は「既定でローカル AI、未起動時は OpenAI にフォールバック」を明記。`memo-ai-panel` Stimulus はキー未設定でも送信可能にし、応答ごとに使用バックエンド（`ローカル` / `OpenAI`）バッジを表示。応答 JSON に `backend` を追加。
* メモパネルは執筆特化（AsciiDoc 出力）の system prompt を維持し、intent ルーティングは通さない（汎用 `Chat::Agent` は独立画面で活用予定）。

=== Phase 5a 実装メモ（完了）

* `Chat::Tools::RagQueryGenerator`（`app/services/chat/tools/rag_query_generator.rb`）— LFM2.5（`ModelRegistry.for(:intent)`）に §3.3 `RAG_QUERY` で JSON 検索語を生成。失敗時はユーザー原文をそのままクエリにフォールバック。

=== Phase 5b 実装メモ（完了）

* **DB**: `memo_embedding_chunks` テーブル（`memo_id` / `chunk_index` / `content`）。`pgvector` は OS に拡張がある環境でのみ migration が `embedding vector(1024)` + HNSW インデックスを追加。`schema.rb` には vector 型を載せない（Rails schema dump 非対応）。`MemoEmbeddingChunk.pgvector_enabled?` で実行時判定。
* `Chat::EmbeddingClient` — llama-server `/embedding`（`query:` / `passage:` prefix）。`ConnectionError` で接続失敗を識別。
* `Chat::ModelRegistry` — `embedding` 役割（既定ポート `10034`）。`build_embedding_client`。
* `Chat::MemoChunker` — タイトル + 本文を ~1,800 文字単位で分割（LFM2.5 short-context 向け）。
* `Chat::Tools::MemoEmbeddingIndexer` + `MemoEmbeddingIndexJob` — メモ保存時（`title` / `body` 変更）に非同期インデックス。`bin/rails kbmemo:embeddings:backfill` で既存メモ一括。
* `Chat::Tools::RagSearch` — pgroonga（lexical）と pgvector 近傍（semantic）を **RRF** で統合。Embedding サーバ未起動時は semantic をスキップし 5a 単独で動作。`Result#semantic_used` で semantic 寄与の有無を返す。
* embedding 未導入環境（pgvector なし）ではチャンクテーブルのみ作成され、lexical RAG は従来どおり動作。

=== Phase 8 実装メモ（完了）

* **DB**: `agent_chat_conversations`（`account_id`、任意 `memo_id`、`title`）/ `agent_chat_messages`（`role`、`content`、`intent`、`model_role`、`metadata` jsonb）。
* `AgentChat::ConversationStore` — アカウント単位の会話取得・ターン追記・履歴消去。
* `AgentChatsController` — `create` で user/assistant を永続化、`show` で直近会話を UI へ復元、`destroy` で履歴消去。
* Stimulus `agent-chat` — `conversation_id` 付き POST、DELETE でサーバ側クリア。ページ再読込で履歴復元。
* **会話一覧 UI** — サイドバーに `updated_at` 降順のスレッド一覧。`?conversation_id=` で切替、`?new=1` で新規チャット。「この会話を削除」後は新規画面へ遷移。

=== Phase 9 実装メモ（完了）

* `Chat::NyoyMcpConfig` — `credentials nyoy_mcp` または `NYOY_MCP_URL` / `NYOY_MCP_API_TOKEN`。
* `Chat::NyoyMcpClient` — Nyoy MCP HTTP `tools/call`（stateless JSON）。
* `Chat::Tools::NyoyMcpRunner` — Router の委譲ツール（`web_search` / `fetch_url` / `generate_image` 等）を実行し結果を system コンテキストへ注入。
* `Chat::Agent` — 徒然内 RAG の後に MCP ツールを実行。`fetch_url` は URL 未検出時はスキップ（pending にしない）。`image_analysis` / `memo_add` は引き続き pending。
* 未設定時は従来どおり `pending_tools: true`（MCP 未接続と同じ挙動）。
* **pending_tools UI** — 未実行ツール名を `pending_tool_names` で返し、assistant 応答下に Nyoy MCP 設定／ツール有効化の案内を表示。
* **MCP マージ拡張** — `rag_lookup` / `web_research` で UI 有効時に `recall_memos` / `search_memos` をローカル RAG・Web 検索と併用。`generate_image` 完了時は `mcp.image_urls` を UI プレビュー。
* **画像生成** — `generate_image` でラフ案を表示し、ユーザーが選んだ draft を `refine_image` で仕上げる（<<image-refine-flow,§12>>）。

== 8. テスト方針

* `LlmClient` / `ChatModels` はスタブ HTTP（WebMock 相当）で単体テスト。
* `IntentClassifier` は固定 JSON 応答で分類マッピングを検証。
* ルーター / エスカレーションは LLM 呼び出しをスタブし分岐のみ検証。
* 既存 `memo_ai_chat_test.rb` を回帰として維持。RAG（Phase 5a/5b）は retriever / embed / マージをスタブで単体検証。
* Rails test が sandbox の DB 接続で失敗する場合は `require_escalated` で再実行（`AGENTS.md`）。

== 9. リスク・留意点

* **ローカルサーバ依存**: llama-server / sd.cpp 未起動時のフォールバック（明示エラー・任意で BYOK 経由）を用意。
* **多段呼び出しのレイテンシ**: intent→ツール→統合で往復増。ストリーミングやタイムアウト設計が必要。
* **JSON 逸脱**: 小型モデルの JSON 崩れに備えパーサを堅牢化（§8 dev note）。
* **RAG インデックス**: pgvector 追加で DB サイズ・再インデックスコストが増える。Embedding サーバ未起動時は pgroonga のみにフォールバック（Phase 5a 単独でも動作）。
* **埋め込みモデルの制約**: LFM2.5-Embedding-350M は short-context（~512 tokens/doc）向け。長文メモはチャンク分割が必須。

* **UI の位置づけ**: メモ編集パネルは執筆特化。汎用機能（Web 調査・画像生成）は独立チャット画面または **Nyoy MCP**（<<nyoy-mcp,§11>>）。

如意（Nyoy）が `ChatTools::*` を MCP（`https://nyoy.kbmemo.net/mcp`）で公開した。

=== 11.1 徒然に残すもの

* Vision / SD: `analyze_image`, `generate_image`, `refine_image`, `list_prompt_styles`

[[image-refine-flow]]
== 12. 画像生成の仕上げ（refine）接続（2026-07）

=== 12.1 実装済みフロー

徒然 `/agent_chat` から画像生成を依頼すると、Nyoy MCP `generate_image` を呼び、`get_image_generation` の `draft_urls` をチャット内にラフ案として表示する。
`awaiting_selection` では各ラフ案に **仕上げ** ボタンを出し、ユーザー操作で `refine_image(id, draft_index)` を呼ぶ。
その後は既存の `image_generation_watch` polling で `get_image_generation` を継続し、`completed` の画像 URL をチャットに追加表示する。

=== 12.2 Nyoy MCP 契約

如意の SD パイプラインは次の段階を持つ（正本: 如意 `docs/mcp-server.md`）。

[source,text]
----
generate_image
  → get_image_generation（status: drafting → awaiting_selection）
  → refine_image（draft_index: 0..3）
  → get_image_generation（status: refining → completed）
----

=== 12.3 接続点

[cols="1,2,2"]
|===
|領域 |実装 |状態

|`Chat::Tools::NyoyMcpRunner`
|`generate_image` 後に状態確認。`awaiting_selection` で `image_urls`（ラフ）と `image_generation_watch` を返す。`refine_image` は直接実行可能ツールに含める
|自動 chaining はしない。`draft_index` は UI 操作または自然文選択で決める

|`Chat::Agent`
|`image_generation` intent で `generate_image` を直接呼ぶ
|ユーザーが自然文で「2 番を選んで」と送った場合は、直近の `awaiting_selection` 画像生成を `refine_image(draft_index=1)` に解釈して実行

|Agent Chat UI
|ラフ案の `<img>` プレビュー、draft ごとの **仕上げ** ボタン、`image_generation_watch` によるクライアントポーリング
|仕上げ後の画像は同じ応答内でラフ案を置き換えて表示する

|会話永続化
|`mcp.image_urls` / `image_generation_watch` を metadata に保存。polling / refine の完了画像 URL は `conversation_id` 付き status API で同じ assistant message に merge 保存する
|自然文で選択した draft 番号も assistant message の `mcp.image_generation_watch` として保存済み
|===

=== 12.4 補足

* `refine_image` はユーザー選択を伴うため、`generate_image` 直後に自動実行しない。
* Nyoy 側の詳細画面を開く導線（`show_path`）は、画像 URL が得られない場合のフォールバックとして維持する。
* 完成画像も Active Storage URL の場合はラフ案と同じ扱いで直接表示する。必要が出た時点でプロキシ要否を再検討する。

関連: 如意 `docs/architecture/nyoy-mcp.adoc` §9、如意 `docs/ecosystem-roadmap.md` §6（徒然側）。
