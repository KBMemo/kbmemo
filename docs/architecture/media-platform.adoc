= Tsuzura（葛籠）— メディアプラットフォーム設計方針

KBMemo で写真・画像を **大規模に扱い・編集し・共有する** ための全体設計。
**製品名 Tsuzura**（葛籠・つづら）。Phase 0 方針 + **Phase 1・2 完了**（2026-06）。**Phase 3 着手**（crop/rotate・EditStack）。実装は別リポジトリ（`kbmemo-media`）＋ KBMemo 連携。Phase 2: link:tsuzura-phase2.adoc[tsuzura-phase2.adoc]、Phase 3: link:tsuzura-phase3.adoc[tsuzura-phase3.adoc]。

前提: `AGENTS.md`（メモ本文の正は DB の AsciiDoc）、link:memo-body-editor-roadmap.adoc[memo-body-editor-roadmap.adoc]（Phase 5f 現行 Git アセット）、link:google-calendar-sync.adoc[google-calendar-sync.adoc]（外部サービス連携の先例）、link:google-photos-integration.adoc[google-photos-integration.adoc]（Google フォト取り込みは Tsuzura の入力源の一つ）。

== メモ添付と Tsuzura の使い分け [[memo-vs-tsuzura]]

[cols="2,2,2"]
|===
| |**メモ添付（Git `MemoAssets`）** |**Tsuzura（葛籠）**

|向くもの
|スクショ 1 枚、図の PNG、**そのメモ専用** の小ファイル
|旅行写真 **一括**、アルバム、**複数メモから参照** したい原本

|上限の目安
|1 ファイル 10MB、Git commit 単位
|枚数・総量 **大**（ストレージは Active Storage → 将来 RustFS）

|本文記法
|`image::filename.jpg[]`（相対・Git アセット）
|`image::media:01JHB…[]` / `album::01JHA…[]`（ULID）

|公開
|メモの `visibility` に従う（`/memos/:id/assets/...`）
|メモ show 経由で Tsuzura URL 解決（**メモが見えないと画像も見えない**）

|オフライン Git
|メモと一緒に clone 可能
|不可（DB + blob が正）
|===

**UI 文案（案）:**

* メモ編集ヘルプ: 「**1〜2 枚の添付** → メモに直接アップロード。**大量の写真** → Tsuzura（CLI で登録して `image::media:` で挿入）。」
* Tsuzura CLI 完了時: 「KBMemo メモに以下を貼り付け:」+ AsciiDoc 断片

**移行:** Git アセットから Tsuzura への自動移行は **Phase 1 非ゴール**。必要なら将来 `tsuzura import --from-memo` を検討。

== AsciiDoc 参照（ULID） [[asciidoc-ulid]]

* **Album ID** / **MediaItem ID** はいずれも **ULID**（`Memo#uid` と同じ `UID_FORMAT`）。
* マクロ内の ID は **小文字可**（正規化して lookup）。

[source,asciidoc]
----
= 2024 夏 北海道

album::01JHABCD1234567890ABCDEF[]

函館の朝。

image::media:01JHBCDF1234567890ABCDEF[width=720]
image::media:01JHBCEF1234567890ABCDEF[]
----

* `album::` … Tsuzura がアルバム内サムネグリッド（または先頭 N 枚）を HTML 化
* `image::media:…` … 1 枚。`media:` プレフィックスで Git アセットと区別（`MemoDiagramMacro` 同型の拡張）

**properties（任意）:**

[source,json]
----
{
  "media_album_id": "01JHABCD1234567890ABCDEF",
  "media_item_ids": ["01JHBCDF1234567890ABCDEF"]
}
----

== ストレージ（Active Storage → S3 互換）

=== Phase 1

* **Rails Active Storage**、`config.active_storage.service = :local`
* 本番ディスク: 例 `/home/kensei/sites/kbmemo-media/storage`（容量監視必須）
* サムネ（thumb / web）は **アップロード Job** で生成し、別 blob として保存（Phase 1 最小: web のみでも可）

=== 移行（Phase 後半）

* 目的: **RustFS** 等の **S3 互換** バックエンド（ベータ終了後に本番切替を検討）
* 手順案: `active_storage` の `mirror` / `direct_upload` 設定変更 + `rails active_storage:migrate` 相当の blob コピー Job
* **URL 契約を変えない:** KBMemo 本文の ULID と Tsuzura API は不変。バックエンドのみ差し替え

== デプロイ（nginx）

link:../deployment/production.adoc[production.adoc] の kbmemo と同型。

[source,text]
----
https://media.kbmemo.net
  → nginx server_name media.kbmemo.net
  → proxy_pass http://127.0.0.1:3008  （Tsuzura Thruster+Puma）
  → TLS: certbot -d media.kbmemo.net
----

* **Cookie:** Rodauth 共有時は `domain: .kbmemo.net` を両アプリで揃える
* **CORS:** Phase 2 で `rack-cors`（`/v1/*`、`TSUZURA_CORS_ORIGINS`）。ピッカーは KBMemo 同一オリジン API 経由が主経路
* **デプロイ:** `kbmemo-media/bin/deploy`（`db:migrate` 必須）。nginx 一括 import 向け `client_max_body_size` **512M 以上** 推奨 — link:../deployment/production.adoc#tsuzura-nginx[production.adoc]

== 認証（Rodauth 共有） [[rodauth-shared]]

Phase 1 は **方式 A のみ**:

* Tsuzura DB に **同一 PostgreSQL** の `accounts` / Rodauth テーブルを参照（KBMemo と同 DB または read replica — 実装時に 1 本化）
* `app/misc/rodauth_main.rb` 相当を Tsuzura に持ち、**セッション Cookie 名・secret** を KBMemo と共有
* CLI: **ブラウザログイン後の Cookie ファイル**、または **`tsuzura_api_token`**（Clip API 同型・Phase 1 で CLI 専用トークン 1 種で可）

**Phase 1 非ゴール:** サービス間 JWT、Tsuzura 独自ユーザー登録

== 顔検出とプライバシー [[face-privacy]]

**実装タイミング:** Phase 4 以降。**処理場所:** Tsuzura **サーバー**（アップロード済み画像を Job で解析）。

=== 設計原則（推奨・確定方向）

**顔検出データはアカウント（個人）単位で保持し、システム内での共有・横断利用は行わない。**

[cols="1,3"]
|===
|項目 |方針

|スコープ
|`FaceRegion` / 顔クラスタ ID は **`owner_account_id` に紐づく** MediaItem にのみ付随

|他ユーザー
|同一アルバム・グループ共有メモ上の写真でも、**他アカウントの顔検出結果は参照不可**

|横断利用
|全ユーザー横断の顔インデックス、類似顔検索、**学習用データセット化** は **行わない**

|運用・分析
|管理者も **原則閲覧しない**（障害調査時の最小アクセスは監査ログ付き例外とする）

|再検出
|別ユーザーが同じバイト列にアクセスできる場合でも、**検出 Job はそのユーザーの操作時のみ** 走らせ、結果はそのユーザーの MediaItem に紐づく（共有キャッシュしない）
|===

**理由:** 顔座標・クラスタは **生物学的特徴に近いメタデータ** になり得る。個人単位の閉じた利用に限定すると、説明責任・漏えいリスク・「システムが顔を覚えている」不安を抑えられる。

**共有メモとの関係:** 公開されるのは **ぼかし済み画像（Rendition）** のみ。顔検出の生データは **編集者アカウント内** に留める。

=== 利用目的（サービス説明用）

* 共有前に **プライバシー保護**（顔のぼかし）を支援するため、**当該アカウントがアップロードした** 写真内の **顔の位置** を自動検出する。
* **顔認証・特定個人の実名识别** には使用しない。
* **他ユーザーのデータとの突合・プロファイリング** には使用しない。

=== プライバシーポリシー文案（ドラフト）

____
【Tsuzura（葛籠）— 顔検出機能に関する説明】

1. 概要
Tsuzura の顔検出機能は、お客様が写真を共有する前に、写り込んだ顔をぼかすなどのプライバシー保護を行いやすくするための補助機能です。

2. 処理する情報
• お客様が Tsuzura にアップロードした画像データ
• 当該お客様の画像から得られる顔領域の座標情報（バウンディングボックス）および、**当該お客様のアカウント内でのみ** 意味を持つ匿名の内部 ID（人物クラスタ用）

3. 利用目的
• **お客様本人** の顔のぼかし等の編集処理の提案・適用
• **お客様本人** の共有前確認（未処理の顔がある場合の警告表示）

4. 行わないこと
• 第三者への顔データの販売・提供
• 本人確認や広告ターゲティングのための利用
• KBMemo / Tsuzura 内の **他のお客様** のデータとの共有・突合・横断分析
• サービス改善のための **顔データの学習利用**（モデル改善は匿名化された合成データ等、別途明示した場合を除く）
• 生体認証

5. 保存と分離
• 顔検出結果は **お客様ごとのアカウントに紐づけて** 保存します。他のお客様や運営者が、お客様の顔検出結果を **一覧・検索・再利用することはありません**（法令・障害対応等、必要最小限の例外を除く）。
• 共有アルバムや KBMemo 上の公開メモを通じて他者が画像を閲覧できる場合でも、**顔検出のメタデータ自体は公開されません**。

6. 保存期間
• 顔座標・内部 ID は、編集完了後またはお客様が当該メディアを削除した時点から **90 日以内** に削除する（方針案。実装時に確定）。
• 元画像は Tsuzura の通常のメディア保存期間に従う。

7. 第三者提供
法令に基づく場合を除き、顔検出結果を第三者に提供しません。解析処理を外部 API に委託する場合は、契約上の DPA を締結し、**当該お客様の当該画像の処理に限定** し、委託先での二次利用を禁止します。

8. お客様の選択
顔検出は任意機能です。手動でのぼかしのみを利用することもできます。自動検出結果は、共有前に必ずプレビューで確認できます。

9. お問い合わせ
kbmemo.net の運営者連絡先（本番運用開始時に URL を記載）までご連絡ください。
____

== 動画配信と CDN [[video-delivery]]

=== 「公開 CDN」とは

**CDN（Content Delivery Network）** は、動画・画像ファイルを **世界中のエッジサーバーにキャッシュ** し、視聴者の近くから配信する仕組み（Cloudflare、CloudFront 等）。

* **メリット:** 大規模配信・海外向け・オリジン帯域の削減
* **デメリット:** 設定・コスト・**公開 URL の拡散**（キャッシュ・署名管理）

=== 方針（帯域コストを低く）

Phase 1 では **動画機能なし**。将来 Phase 5 で動画を足すときも、**最初は CDN なし** でよい。

[cols="1,3"]
|===
|施策 |内容

|配信経路
|**nginx → Tsuzura（または RustFS）** のみ。公開バケットに生 URL は置かない

|認可
|**MemoPolicy 連動の signed URL**（短 TTL）。一覧ページで `<video autoplay>` 禁止

|エンコード
|720p 上限・H.264・適度なビットレート（スライドショー用途）

|画像
|web 用リサイズ済み Rendition のみ配信。原本 DL はオーナーのみ

|キャッシュ
|nginx `proxy_cache` またはブラウザ `Cache-Control`（private）。**全公開 CDN は必要になるまで導入しない**

|帯域監視
|nginx access log + アラート。月次上限の soft cap（運用で決定）
|===

**まとめ:** 「公開 CDN」= 別途 CDN サービスで動画を世界中配信すること。**低帯域優先** なら **認証付き直配信 + 小さい派生ファイル** で足り、KBMemo 個人〜小規模運用では Phase 5 初期も CDN 不要。

== 背景：現行 KBMemo の画像

[cols="1,3"]
|===
|現状 |限界

|`MemoAssets` + Git `{slug}.assets/`
|メモ添付の小ファイル向け。10MB/ファイル、メモ単位 commit

|本文 `image::filename[]` + `imagesdir`
|メモ内表示は成立。メモ横断ライブラリ・編集版管理なし

|`MemoPolicy` / `visibility`
|メモ単位の共有。画像コレクション単位の UX なし

|Clip API + `ClipImageImporter`
|公開 HTTP 画像の取り込み。Google フォト等の認証付き源は別途
|===

**規模感（要件）:** 画像ストレージはメモ本文に比べ **おおよそ 1000 倍** を想定する。

== プロダクト像

=== Tsuzura（`kbmemo-media`）

`media.kbmemo.net` で公開する写真・動画アプリ。写真・動画アセットの **保管・整理・加工・配信** を担う。

* 一括アップロード（EXIF 付き）
* アルバム（写真集）
* 編集（トリミング、回転、顔のぼかし等）
* 選択写真からのショート動画生成
* 外部クライアント向け API

=== KBMemo（既存 `kbmemo_site`）

**文章・ストーリー・公開範囲** を担う。

* アルバムに付随する **長文メモ**（旅行記、キャプション、Wiki リンク）
* **メモ URL で本文ごと共有**（公開 / グループ）
* Notebook・カンバン等、既存プロダクトとの統合
* Tsuzura 参照マクロの **表示時解決**

== KBMemo と Tsuzura の境界

[cols="2,2,2"]
|===
|関心 |Tsuzura |KBMemo

|バイト列（原本・派生・動画）
|◎ |×

|アルバム構造・並び・EXIF 索引
|◎ |参照のみ

|トリミング・回転・顔ぼかし
|◎ |×

|スライドショー動画生成
|◎ |×

|AsciiDoc 本文・Wiki リンク
|× |◎

|公開範囲（public / group / owner）
|Tsuzura 側は **KBMemo 判定に従う派生 URL** を推奨 |◎（正）

|Notebook / カンバン / タグ
|× |◎

|Git 作業ツリー
|× |メモ `.adoc` のみ（画像 Git 化は小物のみ継続）
|===

**原則:** 画像の「加工と籠への収納」は Tsuzura。「意味と公開の物語」は KBMemo。

== データモデル（案）

=== Tsuzura 側（`kbmemo-media`）

[cols="1,3"]
|===
|エンティティ |概要

|`Album`
|id（**ULID** PK）、タイトル、説明（短）、cover_media_id、owner_account_id、日付範囲

|`MediaItem`
|id（**ULID** PK）、kind（image / video）、checksum、width/height、EXIF JSON、captured_at。バイトは **Active Storage** attachment

|`AlbumItem`
|album_id、media_item_id、position

|`MediaRendition`
|media_item_id、variant（thumb / web / edited）、storage_key

|`EditStack`
|media_item_id、非破壊編集 JSON（rotate、crop、blur_regions[]）

|`VideoExport`
|入力 media_ids[]、status、output_media_item_id、ffmpeg パラメータ

|`FaceRegion`（任意・Phase 後半）
|検出框、cluster_id、blur 対象フラグ
|===

=== KBMemo 側

AsciiDoc の ULID 記法は「<<asciidoc-ulid,AsciiDoc 参照（ULID）>>」を正とする。

**アルバムとメモの関係（案）:**

* 1 アルバム : 0..1 **メインメモ**（KBMemo `Memo`、`properties.media_album_id`）
* または 1 Notebook : 1 アルバム（旅行記ノートブック）

== 機能詳細

=== 一括登録

* API: `POST /v1/media/batch` または presigned URL 連続 PUT
* EXIF `DateTimeOriginal` → `exif_captured_at` / GPS、`file_mtime` 保存。日付アルバムは EXIF 撮影日があるもののみ（**W2 完了** — link:tsuzura-watch-import.adoc[tsuzura-watch-import.adoc]）
* 重複排除: `checksum` 同一なら `MediaItem` を再利用（**W1 完了** — link:tsuzura-watch-import.adoc[tsuzura-watch-import.adoc]）

=== 画像編集

[cols="1,2,1"]
|===
|機能 |方式 |Phase

|回転・トリミング
|EditStack + 新 Rendition
|3

|手動ぼかし矩形

|3

**編集の正:** 非破壊 **EditStack** を推奨（原本 blob は保持、表示は派生 Rendition）。

=== ショート動画

* 入力: 選択 `media_item_ids[]`、表示秒数、トランジション、解像度
* 処理: Tsuzura 内 Job + **ffmpeg**（Solid Queue 相当の worker。**KBMemo Puma 内では実行しない**）
* 出力: 新 `MediaItem`（kind: video）または `VideoExport` レコード
* KBMemo 本文: `video::media:01HVIDEO[]` または既存 video マクロ拡張（YouTube 以外の self-host）

=== Google フォト

* 取り込み **先** は Tsuzura（バイト + メタ）
* KBMemo 連携は「アルバム取り込み後にメモ作成」
* 詳細: link:google-photos-integration.adoc[google-photos-integration.adoc]（本 doc の入力チャネルとして位置づけ）

=== 画像の閲覧

**推奨:** メモ経由の表示では **KBMemo `MemoPolicy#show?` が通った場合のみ** Tsuzura が signed URL を発行。

* Tsuzura に独自 public フラグだけ持つと、メモとズレやすい
* アルバム単体 URL は Tsuzura 側 `AlbumPolicy`（将来）

=== 外部 API

* KBMemo `clip_api_token` と同型の **Tsuzura CLI トークン**（`account.tsuzura_api_token_*` 等 — Phase 1 は CLI 用のみ）
* スコープ: upload / read / album_manage
